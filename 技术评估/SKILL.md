# 内部技术评估范式（技术评估）

> 沉淀自 RFID 过账项目内部评估（泰国工厂，2026-11）：现场照片裁剪标注 +
> 6 设备网络架构 + 传统/AI 工作量对比 + 甘特图 + 三档定价 + 接/不接决策矩阵。
> 适用于工业上位机、机器视觉、嵌入式、数据采集、网络改造、旧系统迁移、软件集成等项目。
> **弱模型照抄执行**：脚本干粗活，判断由人给定，AI 只做整理和写作；不许编数字，不许跳过核验。

## 0. 执行卡（弱模型只看这一段也能做对）

**顺序不能变：先出图，再写文，最后核验。**

1. `init_project.py` 建目录和 `project.json`。
2. 图片放 `assets/raw/`；在 `project.json` 填 `crop` / `annotations`。
3. 跑 `crop_annotate.py`，**必须打开输出图目检**：桌面、任务栏、显示器边框是否裁掉。
4. 跑 `make_charts.py`，按需生成 5 张图。
5. 跑 `new_report.py` 生成骨架。
6. **先读 `templates/example_report.md`**，照它的密度和句式填每一节；禁止留空、禁止写“待定 / 需进一步确认”。
7. 跑 `verify_report.py --strict`，**0 FAIL 0 WARN 才准交**。
8. 不过就按 FAIL 提示改，改完重跑；**同一处改 3 次还不过，停下来问人**，不要绕开检查。

**弱模型三条禁令：**

- 不许自己判断“能不能接 / 多少人天 / 报多少钱”——这三个结论必须由人给，模型只负责组织成文档。
- 不许删检查项、改 `verify_report.py` 让自己通过。
- 不许只交骨架，或只填一半表格。

## 一、何时用我

- 用户说"做个技术评估 / 内部评审 / 可行性分析 / 工作量评估 / 风险分析"；
- 用户问"这个项目能不能接 / 值不值得做 / 大概要多久 / 要投多少人"；
- 手里有现场照片、软件截图、设备清单、旧程序、接口文档，需要整理成内部文档；
- 需要把评估结论沉淀成可复用的文档，供团队讨论或领导决策。

**不适用**：对客户的正式报价单（用「上位机报价」skill）、纯技术方案书、投标文件。

## 二、三条铁律（违反任何一条，文档作废）

1. **必须标内部。** 标题区写"内部文档，勿外发"，文末再写一次"仅限内部使用"。文档里会有底线价、毛利、谈判话术，误发客户等于裸奔。
2. **每个数字有出处。** 人天、概率、价格、工期，要么来自脚本统计，要么来自 project.json，要么写明"假设"。禁止拍脑袋编一个看起来专业的数字。
3. **每个未知项有验证动作。** 不许写"需进一步确认"就完事，必须写"谁、用什么方法、什么时候拿到"。每条风险必须有对策和触发信号。

## 三、开工五问（不答完不动手）

| # | 问题 | 影响 |
|---|---|---|
| 1 | 项目类型是什么？工业上位机 / 视觉 / 嵌入式 / 网络 / 旧系统迁移？ | 决定章节重点和图表类型 |
| 2 | 文档给谁看？技术团队 / 老板 / 销售？ | 决定写多深、要不要放价格 |
| 3 | 手里已有什么？照片、截图、旧程序、IO 表、接口文档、抓包？ | 决定评估是"看图说话"还是"动手验证" |
| 4 | 最大的未知是什么？接口 / 协议 / 现场配合 / 付款？ | 决定 P0 未知项和红线 |
| 5 | 时间压力？本周要结论，还是可以调研两周？ | 决定做不做 POC、排期乐观还是现实 |

用户答不上来的，按默认值走，并在文档 §0 标注"假设"。**不要因为信息不全就不写，先把未知项变成行动清单。**

## 五、五步流程

### 第 1 步：初始化

```powershell
$SKILL = "$env:USERPROFILE\.config\opencode\skills\技术评估"
$PROJ  = "E:\项目\xxx评估"

python "$SKILL\scripts\init_project.py" $PROJ `
  --name "项目名" --type "工业上位机" --client "客户/现场" --deadline "2026-12-31"
```

产出：`project.json`、`assets/raw/`、`report/`。

### 第 2 步：收集素材

优先顺序：用户给的文件 → 工作目录已有图片 → opencode 会话里上传过的图片。

```powershell
# 先看会话里有什么图（不保存）
python "$SKILL\scripts\extract_images.py" --list

# 保存最近 5 张到 assets/raw
python "$SKILL\scripts\extract_images.py" --outdir "$PROJ\assets\raw" --latest 5

# 指定会话
python "$SKILL\scripts\extract_images.py" --session-id ses_xxx --outdir "$PROJ\assets\raw"
```

拿到图后先**目检**：是不是目标图、清晰度够不够、有没有拍到敏感信息（人名、工号、客户 logo）。不合适的不要用。

### 第 3 步：出图

编辑 `project.json` 的 `images` 和 `charts`，然后：

```powershell
python "$SKILL\scripts\crop_annotate.py" --config "$PROJ\project.json"
python "$SKILL\scripts\make_charts.py"   --config "$PROJ\project.json"

# 只重做某一张
python "$SKILL\scripts\crop_annotate.py" --config "$PROJ\project.json" --only ui_annotated
python "$SKILL\scripts\make_charts.py"   --config "$PROJ\project.json" --only timeline
```

**先出图，再写文档。** 图定了，正文的结构和重点就定了；反过来一定对不上。

### 第 4 步：写文档

```powershell
python "$SKILL\scripts\new_report.py" --config "$PROJ\project.json"
```

生成 `report/<项目名>_内部技术评估_<日期>.md`，按模板注释逐节填写。写作要求见第八节。

**写之前先打开 `templates/example_report.md`。** 弱模型最常见的失败不是格式错，是每节只写一句话、表格填“待定”。样例展示了合格的密度：结论带数字、未知项带责任人和截止、风险对策能落地、行动有产出。

判断（能不能接、多少人天、报多少钱）必须先有人给定；模型只负责把判断组织成文档，不要让它从零猜。

### 第 5 步：核验

```powershell
python "$SKILL\scripts\verify_report.py" "$PROJ\report\xxx.md" --config "$PROJ\project.json"
```

- `PASS`：通过；`WARN`：建议修；`FAIL`：必须修。
- 交付前要求 **0 FAIL**；重要文档加 `--strict`，要求 0 WARN。
- 纯文字项目没有截图时加 `--min-images 0`。

核验分两层：

| 层 | 查什么 | 典型 FAIL |
|---|---|---|
| 结构层 | 章节、图片、表格列数、占位符、数字一致 | 缺风险章节、图片路径错、数字对不上 |
| 内容层 | 结论是否明确、未知项是否有动作、风险对策是否落地、行动是否落实 | 结论写“需进一步调研”、责任方写“待定”、对策写“加强管理” |

**核验通过只是下限，不是质量认证。** 交付前再对照 `example_report.md` 抽查三处：结论有没有数字、风险有没有触发信号、行动有没有负责人和截止。

## 六、project.json 配置

```json
{
  "project": {
    "name": "项目名",
    "date": "2026-11-28",
    "type": "工业上位机",
    "client": "客户/现场",
    "deadline": "2026-12-31"
  },
  "images": [
    {
      "src": "assets/raw/img_001.jpg",
      "out": "assets/ui_annotated.png",
      "crop": [165, 510, 1190, 1240],
      "scale": 1.5,
      "side": 330,
      "annotations": [
        {"box": [45, 560], "color": "#1E6EDC", "label": "工厂内网", "sub": "设备一 ~ 四", "label_y": 300}
      ]
    }
  ],
  "charts": [
    {"type": "architecture", "out": "assets/architecture.png", "left_nodes": [], "center": {}, "right": {}},
    {"type": "workload", "out": "assets/workload.png", "items": []},
    {"type": "timeline", "out": "assets/timeline.png", "tasks": [], "milestones": []},
    {"type": "risk_matrix", "out": "assets/risk_matrix.png", "risks": []},
    {"type": "scenario", "out": "assets/scenario.png", "items": []}
  ],
  "numbers": [
    {"key": "总投入", "value": "15~20 人天"},
    {"key": "建议报价", "value": "14.8 万"}
  ]
}
```

| 字段 | 说明 |
|---|---|
| `images[].crop` | `[x1, y1, x2, y2]`，只保留软件窗口/有效区域，越界会自动裁到边界 |
| `images[].scale` | 放大倍数，截图小就用 1.3~1.5，别超过 2（糊） |
| `images[].side` | 右侧标签栏宽度，有标注时生效，建议 300~360 |
| `images[].annotations[].box` | `[y1, y2]`，横向铺满图片；一个框对应一组信息 |
| `images[].annotations[].rect` | 可选，`[x1, y1, x2, y2]` 局部框；不填则用 `box` 通栏 |
| `images[].annotations[].label_y` | 标签在右栏的垂直位置，用来错开避免重叠 |
| `charts[].type` | `architecture` / `workload` / `timeline` / `risk_matrix` / `scenario` |
| `numbers` | 核验用的关键数字，必须原样出现在文档里，防止正文和图/表对不上 |

`project.json` 是唯一事实源：改数字先改这里，再改文档，最后跑核验。

## 七、图表选型

| 图 | 什么时候用 | 关键要求 |
|---|---|---|
| 截图标注 `crop_annotate` | 有现场界面、配置页、设备照片 | 裁剪干净，右侧标签，不遮内容 |
| `architecture` | 有设备→上位机→服务器/MES 的拓扑 | 标清 IP:端口、协议、网段、工位映射 |
| `workload` | 有分模块人天 | 两列对比（传统 vs AI / 方案 A vs B）+ 数值标签 |
| `timeline` | 有排期 | 任务条 + 3 个里程碑，日期用 `YYYY-MM-DD` |
| `risk_matrix` | 风险 ≥3 条，想直观展示优先级 | 概率/影响 0~1，标签不重叠 |
| `scenario` | 可行性分场景 | 概率合计 100%，每条带工作量 |

图不是越多越好。**一页纸能说清就不做第二张图。** 常规组合：截图 + 架构 + 工作量 + 甘特，4 张够用。

## 八、文档结构（12 节）

| 节 | 写什么 | 红线 |
|---|---|---|
| 0 结论速览 | 可行性 / 工作量 / 报价或投入 / 最大风险 / 建议动作 | 5 行以内，必须给结论，禁止"需进一步调研" |
| 1 背景与现状 | 谁、在哪、现在用什么、覆盖多少设备/工位 | 只写事实，附裁剪图，不放整张原图 |
| 2 输入与事实 | 逐条列已确认信息，标来源（截图/口述/文档/抓包） | 不把推测写成事实 |
| 3 未知项 | 未知项 / 影响 / 验证方法 / 优先级 / 责任方 / 截止 | P0 ≤5 条，每条有动作和截止 |
| 4 可行性 | 场景 / 概率 / 工作量 / 判断依据 | 概率合计 100%，依据写"看到什么" |
| 5 工作量 | 模块 / 传统 / AI / 说明 + 合计 | 必须两列对比 + 合计；写清 AI 杠杆和瓶颈 |
| 6 风险 | 风险 / 等级 / 能否化解 / 对策 / 触发信号 | 每条有对策，禁止只列风险 |
| 7 信息清单 | 红线 / 重要 / 加分 | 红线 ≤4 条，每条写"拿不到怎么办" |
| 8 周期 | 乐观 / 现实 / 悲观 + 合同工期写法 + 降级方案 | 工期按"资料到位日"起算，不按签约日 |
| 9 定价与成本 | 三档 + 底线 + 成本毛利 + 付款 + 增项 | 内部数据，标"勿外传"；非销售项目改"投入估算" |
| 10 决策 | 绿灯 / 黄灯 / 红灯 | 写死"踩中两个红灯不签" |
| 11 行动 | 动作 / 负责人 / 截止 / 产出 | 本周能启动的排前面 |
| 12 话术（可选） | 客户可能问的 3~5 个问题 | 不硬推，给客户选择权 |

**写作语气**：短句、结论先行、能用表格不用段落。技术判断要敢下结论，但必须写依据和验证方法。

## 九、截图裁剪与标注规范

1. **只留有效区域**：软件窗口/配置区/设备铭牌，去掉桌面图标、任务栏、显示器边框、胶带、反光、手指。
2. **右侧加白边放标签**，不要用半透明框盖住界面文字；框只做浅填充 + 描边。
3. **颜色语义固定**：蓝=内网/设备，绿=专网/第二网段，橙=服务器/外部接口，紫=参数/业务规则。
4. **标签写"是什么 + 范围"**：`10.63.11.x 工厂内网 / 设备一 ~ 四`，不写"这里""那边"。
5. **一张图最多 5 组标注**，多了拆图或改用架构图。
6. **原图只放 `assets/raw/`**，不进文档；文档只引用裁剪后的图。
7. 图片路径统一相对路径 `assets/xxx.png`，换机器也能打开。
8. 整行/整段用 `box` 通栏；只标局部面板用 `rect`（如右上角状态区、某个弹窗）。

## 十一、常见坑

1. **先写文档后找图** → 图对不上正文。先出图再写。
2. **整张截图直接放** → 桌面图标、任务栏全露，显得不专业。
3. **标注框盖住关键数字** → 用右侧标签，不要盖内容。
4. **只写"工作量约 X 天"** → 必须拆模块 + 两列对比 + 合计。
5. **风险只列不写对策** → 核验脚本会打回。
6. **工期按签约日起算** → 资料不到位必延期；按"资料到位日"。
7. **报价只写总价** → 三档 + 底线 + 增项，否则客户一压就没空间。
8. **忘记内部标记** → 可能误发客户，价格底线全暴露。
9. **图片用绝对路径** → 换机器打不开，统一相对路径。
10. **图表中文变方块** → 脚本已内置字体回退；仍失败就装微软雅黑/Noto Sans CJK。
11. **文档里写"从截图读出"** → 直接陈述事实，图只做佐证。
12. **不跑核验就交付** → 必跑 `verify_report.py`，0 FAIL 才算完。
13. **核验全绿就以为质量合格** → 核验只是下限；对照 `example_report.md` 看密度，别交“形式完整、内容空洞”的文档。
14. **让弱模型自己判断能不能接** → 判断由人给，模型只负责整理；否则它会写出一堆“需进一步确认”。

## 十三、模型能力与分工（换模型前必读）

| 模型档位 | 适合做什么 | 不适合做什么 | 正确用法 |
|---|---|---|---|
| 强模型 | 判断可行性、识别隐藏风险、估工作量、写结论 | —— | 可自由写作，核验兜底 |
| 中等模型 | 按样例填表、整理事实、生成图表配置 | 从零判断能不能接 | 必须给 `example_report.md` 和明确结论 |
| 弱模型 | 跑脚本、填模板、抄句式、核对数字 | 判断、估算、识别隐藏风险 | 只做“填空”，判断由人/强模型先定 |

**结论：弱模型能把“格式和表达”做到不掉档，但“判断质量”不能靠它。**

要保证文档质量不变，必须把判断结果先定下来：

1. 谁：项目负责人 / 售前 / 技术负责人。
2. 给什么：可行性档位、人天区间、报价底线、最大风险、接不接。
3. 模型只做：把上述结论写进 `project.json` 的 `numbers`，再按 `example_report.md` 展开成文档。

**判断没定，不要开始写。** 弱模型从零判断，产出一定是“需进一步调研 + 加强管理 + 待定”。

**一句话总结**：评估文档的价值不在"写得多全"，而在"敢下结论、数字有据、风险有解、下一步能执行"。
